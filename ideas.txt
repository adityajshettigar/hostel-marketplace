# Smart Hostel Marketplace — Codex Build Playbook

Paste each numbered prompt into Codex in order. Each phase assumes the previous one is committed. Everything is free-tier: Next.js + Docker locally, free-tier Postgres/Redis/object storage in prod, no paid AI API required.

**One honesty note before you start:** a payment escrow that is *"100% foolproof, zero security risk"* isn't something any codebase (free or paid, student or FAANG) can honestly promise — real escrow systems go through audits, pen-tests, and PCI/RBI compliance review before touching real money. What Codex *can* build well is a **correctly engineered escrow simulation**: real state machine, hashed PIN, idempotent transitions, audit log, Razorpay/Cashfree **test mode**. That's what Phase 6 below does. Treat it as production-*grade code quality*, not production-*cleared for real money* — say so explicitly in your report/demo.

## 0. Stack decisions (context for you, not a prompt)

| Concern | Choice | Why free & simple |
|---|---|---|
| Frontend | Next.js 14 (App Router) | You already asked for it |
| "Microservices" | 5 independent Next.js (API-route-only) apps, each its own repo folder, own Dockerfile, own package.json | Each teammate runs `npm run dev` in their own folder — real service isolation, same language everywhere so nobody's blocked learning a 2nd framework |
| Inter-service calls | Plain REST over Docker network / HTTPS in prod | No message broker needed for a 5-person student build |
| DB | One Postgres **instance**, one **schema per service** (`identity`, `marketplace`, `communication`, `transaction`, `ai`) | Simulates "DB per service" ownership without paying for 5 separate hosted DBs |
| Cache/timer | Redis (Upstash free tier) | Needed for the 48h escrow timer |
| Auth | JWT issued by identity-service, verified by all others via shared public key | Standard, no paid IdP |
| File storage | Cloudinary free tier | Product images, dispute evidence |
| Payments | Razorpay **test mode** | Free, gives you real webhook/signature flow |
| Email | Resend free tier or Gmail SMTP | College-email verification |
| AI | Rule/heuristic-first (median pricing, category from keywords) with an *optional* free Hugging Face inference call — no paid OpenAI key required | Keeps the whole build $0 |
| Deploy | Frontend → Vercel free; each service → Render free web service (or Railway free trial); DB → Neon/Supabase free Postgres; Redis → Upstash free | All $0 tiers |

```

## PHASE 2 — identity-service

```
Inside services/identity-service, implement a Next.js API-route microservice
covering registration, login, session security, and hostel identity, per this
spec (from the SRS):

- POST /api/auth/register: college_email (must match an allow-listed college
  domain list in env var COLLEGE_EMAIL_DOMAINS), full_name, hostel_block,
  room_number, upi_vpa (optional at registration). Send a verification email
  (Resend API) with a signed, expiring token link. Store user in Postgres
  schema "identity", table users, password hashed with argon2.
- GET /api/auth/verify?token=...: verifies email, sets verification_status =
  VERIFIED.
- POST /api/auth/login: email+password → argon2 verify → issue a short-lived
  JWT access token (15 min) + a rotating refresh token (httpOnly cookie, 7
  days) signed with RS256 using a keypair in env vars. Bind the session to a
  device fingerprint hash (from a client-supplied fingerprint header) stored
  in a sessions table.
- POST /api/auth/refresh: rotate refresh token, reject reused/expired ones
  (detect token-reuse attacks by revoking the whole session family).
- Session-IP change handling: if login IP differs from the session's last
  known IP, require a 2FA step (POST /api/auth/2fa/request generates a 6-digit
  OTP emailed to the user, POST /api/auth/2fa/verify checks it) before issuing
  tokens, per SRS 5.7.3.
- GET /api/users/me and PATCH /api/users/me for profile + hostel_block +
  room_number + upi_vpa updates.
- GET /api/users/:id/public — returns only non-sensitive fields (name,
  hostel_block, verification badge) for other services to display seller
  info, per the SRS data-classification rules (UPI VPA and email are never
  exposed here).
- Expose a JWKS endpoint GET /.well-known/jwks.json (public key only) so other
  services can verify JWTs without calling back into identity-service.

Use Zod for input validation on every route, rate-limit /api/auth/login and
/api/auth/2fa/verify (5 requests/minute/IP, in-memory or Redis-based), and
write integration tests (Vitest) for register→verify→login→refresh and for
the new-IP-triggers-2FA path. Add a Dockerfile HEALTHCHECK hitting a
GET /api/health route.
```

```

## PHASE 4 — communication-service

```
Inside services/communication-service, implement chat + chat-safety +
notifications in the "communication" Postgres schema:

- POST /api/conversations (buyer starts a conversation on a listing_id —
  service should call marketplace-service's GET /api/listings/:id to fetch
  seller_id, don't trust a client-supplied seller_id).
- WebSocket or Server-Sent-Events endpoint for real-time delivery
  (use Socket.IO server co-located in this service) — POST /api/messages
  persists, then emits over the socket to the recipient if online.
- Chat Obfuscation Defense (SRS 5.7.2), implemented as a pure, unit-testable
  function `normalizeAndScan(text: string)`:
    1. lowercase, strip spaces/dashes/dots,
    2. convert spelled-out digits ("nine"→"9", "double" prefix handling
       optional),
    3. regex-match 10-digit Indian phone patterns and UPI VPA patterns
       (username@bankhandle),
    4. return { verdict: SAFE|CONTACT_INFO|UPI_INFO|OFF_PLATFORM_REQUEST,
       normalized_text }.
  If verdict !== SAFE, do NOT deliver the message to the recipient — store it
  with safety_result set, return a 200 with a warning payload the frontend
  turns into a toast, per SRS.
  Write at least 15 unit test cases: plain numbers, space-separated,
  dash-separated, spelled-out digits, UPI ids, false-positive-prone normal
  messages containing numbers ("meet at 9"), and obfuscated combos.
- POST /api/notifications (internal-only route, protected by a shared
  service-to-service API key header, not a user JWT) — other services call
  this to create notifications; GET /api/notifications (user's own),
  PATCH /api/notifications/:id/read.

Add Zod validation and Vitest tests for the normalization function
(prioritize this — it's the security-critical piece) plus an integration test
for conversation creation authorization (only the listing's actual buyer/
seller can post in it). Add GET /api/health.
```

## PHASE 6 — transaction-service (escrow, handover, disputes)

```
Inside services/transaction-service, implement the transaction lifecycle,
Smart Escrow simulation, PIN/QR handover, 48h auto-release, and disputes, in
the "transaction" Postgres schema. This is the most security-sensitive
service — follow every point below exactly:

STATE MACHINE (enforce transitions in a single DB function/transaction, never
allow a skip):
DEAL_CONFIRMED → ESCROW_PENDING → ESCROW_LOCKED → HANDOVER_PENDING →
HANDOVER_VERIFIED → COMPLETED
Side paths: ESCROW_LOCKED → DISPUTED → ADMIN_REVIEW → (RESOLVED→COMPLETED or
REFUNDED); HANDOVER_PENDING → (timeout, no state skip) stays until verified,
disputed, or auto-released.

1. POST /api/transactions: called only after marketplace-service confirms an
   offer is ACCEPTED (verify by calling marketplace-service, don't trust the
   client). Creates the transaction row, status DEAL_CONFIRMED.

2. POST /api/transactions/:id/escrow/init: creates a Razorpay Order in
   **test mode** (env vars RAZORPAY_KEY_ID / RAZORPAY_KEY_SECRET — I will add
   these) for the agreed_price, status → ESCROW_PENDING. Return the order id
   to the frontend for Razorpay Checkout.

3. POST /api/webhooks/razorpay: verify the X-Razorpay-Signature HMAC against
   the raw request body using RAZORPAY_WEBHOOK_SECRET before touching
   anything (reject unsigned/invalid immediately, log the attempt). On a
   verified `payment.captured` event, atomically (single DB transaction):
   mark escrow LOCKED, generate a cryptographically random 4-digit PIN
   (crypto.randomInt), store ONLY an argon2 hash of the PIN (never plaintext)
   plus a signed, encrypted QR payload (AES-256-GCM, key from env
   QR_ENCRYPTION_KEY) that encodes {transactionId, expiresAt}, set
   release_deadline = now + 48h, status → HANDOVER_PENDING. Make this webhook
   idempotent (Razorpay retries webhooks — dedupe on event id).

4. POST /api/transactions/:id/verify-handover: seller submits either the PIN
   or a scanned QR string.
   - Rate limit: max 3 attempts per transaction (SRS 5.7.1) — on the 3rd wrong
     attempt, lock the endpoint for that transaction (status field
     handover_locked = true) and require an admin unlock; log every attempt
     (success and failure) to an append-only audit table.
   - Verify PIN via argon2.verify against the stored hash; verify QR by
     decrypting and checking transactionId match + not expired.
   - On success, inside one DB transaction: status → HANDOVER_VERIFIED, then
     immediately attempt the Razorpay payout/transfer call (test mode) to the
     seller's linked account, on success status → COMPLETED, on payout
     failure status stays HANDOVER_VERIFIED with a retry job (do NOT mark
     COMPLETED unless the payout call actually succeeded — no "assume it
     worked").
   - Make the whole verify+payout path idempotent (a duplicate/replayed
     request must not double-pay) using a unique idempotency key per
     transaction stored before calling Razorpay.

5. Auto-release: a Redis-backed job (BullMQ, using the Upstash Redis
   connection) scheduled at escrow-lock time for release_deadline. On fire,
   re-check current status is still HANDOVER_PENDING (not disputed, not
   already completed) before releasing — recheck-then-act inside the same
   flow used for manual verification, so there is exactly one release code
   path, not two. Must survive a service restart (recover pending jobs from
   the DB, not just from Redis, on boot — SRS 5.4.5 / NFR reliability).

6. POST /api/transactions/:id/dispute: buyer only, requires at least one
   uploaded evidence file URL (Cloudinary), sets status → DISPUTED, funds
   frozen (release job for that transaction is cancelled/no-ops if it fires),
   creates an admin_tickets row. PATCH /api/disputes/:id/resolve (admin-only,
   require a second admin's confirmation token if amount > env var
   DUAL_AUTH_THRESHOLD, per SRS 5.7.4) → REFUNDED or back to COMPLETED, always
   appended to the immutable audit log (audit rows are insert-only, no
   UPDATE/DELETE grants on that table for the service's own DB role).

Non-negotiables to implement, not skip:
- All money fields are integers (paise), never floats.
- Every state-changing route runs inside a single Postgres transaction with
  `SELECT ... FOR UPDATE` on the transaction row to prevent race conditions
  (e.g., simultaneous verify-handover + auto-release timer firing).
- Plaintext PIN is never logged, never stored, never returned in any API
  response after the initial generation moment (frontend shows it once to
  the buyer at generation time only).
- Write Vitest tests for: happy path end-to-end, 3-failed-PIN-attempts-locks,
  webhook-signature-rejection, duplicate-webhook-idempotency,
  dispute-freezes-and-blocks-auto-release, and
  auto-release-does-not-fire-if-already-disputed.

At the top of this service's README, add the honesty note: "This escrow
implementation uses Razorpay TEST MODE and has not undergone external
security audit or PCI/RBI compliance review — it is a correctly-engineered
simulation suitable for a student/demo deployment, not a production payments
system." Add GET /api/health.
```

## PHASE 7 — gateway

```
Inside gateway/, implement a thin Next.js API-route reverse proxy that:
- Exposes /api/identity/*, /api/marketplace/*, /api/communication/*,
  /api/transaction/*, /api/ai/* and forwards each to the matching internal
  service URL (from env vars SERVICE_IDENTITY_URL etc, defaulting to the
  docker-compose service names).
- Verifies the incoming JWT (using identity-service's JWKS endpoint, cached
  with a 10-min TTL) on every route except /api/identity/auth/* and
  strips/re-signs nothing — just forwards the original Authorization header
  plus adds an internal X-Service-Key header (shared secret, env var
  INTERNAL_SERVICE_KEY) so downstream services can trust gateway-forwarded
  requests and reject any direct call missing that header.
- Adds basic rate limiting (per-IP, in-memory token bucket) and structured
  request logging (method, path, status, latency) to stdout.
- GET /api/health aggregates each downstream service's /api/health into one
  JSON status report.
```
